# Infra9CORE long-term stability roadmap

## Purpose

Infra9CORE is a versioned generator, not a one-time collection of files. This
roadmap defines how it remains safe, reproducible, and maintainable for generated
repositories over years while preserving manual validation for ordinary changes.

## Operating principles

- Generated project boundaries are a compatibility contract.
- A generator upgrade must never overwrite product-owned application code.
- Each generated repository records the generator release and template contract
  that created it.
- Release checks are explicit release-maintainer actions, not automatic pull
  request or merge pipelines.
- Production infrastructure uses private, signed images selected through
  generated environment configuration.

## 1. Compatibility contract and template identity

### Deliverables

1. Restrict Infra9CORE itself to Node `>=24 <25` and keep `.nvmrc` on the
   supported Node 24 line.
2. Generate a machine-readable `.infra9core.json` manifest containing the npm
   package name, generator version, template-contract version, generation date,
   selected recipes, overlays, package manager, and project identity metadata.
3. Add a compatibility policy describing supported Node, operating-system, and
   application-recipe versions plus a deprecation window.
4. Add a read-only `doctor` mode that validates a generated manifest and reports
   contract drift; it must not edit a project.

### Acceptance criteria

- Every generated project has a valid manifest.
- A project generated by an older contract produces an actionable doctor report.
- Node 25 is rejected before generation.

## 2. Controlled generator and infrastructure upgrades

### Deliverables

1. Define semantic-versioning rules: patch for safe repairs, minor for additive
   recipes/features, major for generated-project contract breaks.
2. Maintain a generated-project upgrade ledger with template contract changes,
   prerequisites, migrations, and rollback guidance.
3. Add a dry-run upgrade planner that compares a generated project manifest with
   an installed generator. It may create a report but never modifies files.
4. Require explicit, reviewed migration commands for any future infrastructure
   upgrade that changes data, image versions, or service topology.

### Acceptance criteria

- Upgrades identify affected generated paths before any write operation exists.
- Every infrastructure migration has reversible and restore-tested guidance.

## 3. Reproducible and secure templates

### Deliverables

1. Preserve private-registry image configuration and document digest pinning for
   every production image reference.
2. Add an image inventory to the generated documentation, including owner,
   immutable digest, update process, signature verification, and rollback image.
3. Define lockfile behavior per selected package manager and recipe; generated
   projects must use one authoritative lockfile strategy.
4. Add a dependency and template update policy that batches reviewed updates into
   release candidates instead of allowing uncontrolled range drift.
5. Add an SBOM and license/security-review runbook for release maintainers.

### Acceptance criteria

- A generated project can identify all production images and their immutable
  source digests.
- Dependency updates are reviewable and reproducible from a clean checkout.

## 4. Explicit release-candidate verification

### Deliverables

1. Keep `tools/release-validate.sh` as the mandatory manual full-stack gate.
2. Add golden generator fixtures for supported recipe combinations and the
   invariant root structure.
3. Cover token rendering, binary asset integrity, argument validation, and
   template manifests in unit tests.
4. Add meaningful health/contract tests to each application recipe rather than
   relying solely on compilation.
5. Record each successful release-candidate run in the GitHub release notes.

### Acceptance criteria

- A release candidate proves generator output and each supported runtime recipe.
- No workflow runs automatically on ordinary pull requests or merges.

## 5. Release governance and package security

### Deliverables

1. Configure npm trusted publishing for `UnifyLK/Infra9CORE`, `publish.yml`, and
   `npm-production`; remove the temporary token immediately after verification.
2. Protect `main` from force pushes/deletions and restrict releases/tags to
   maintainers without requiring merge-time workflow checks.
3. Add `CHANGELOG.md`, `SECURITY.md`, `CODEOWNERS`, contribution guidance, issue
   templates, and a support/deprecation policy.
4. Retain tag/version/main-ancestry release checks and publish provenance for all
   post-bootstrap npm releases.
5. Establish a release-owner rotation and npm/GitHub recovery runbook.

### Acceptance criteria

- A compromised developer machine cannot independently publish a package.
- Every release maps to an immutable tag, source commit, changelog entry, and
  provenance record.

## 6. Generated-project production operations

### Deliverables

1. Maintain Supabase migration, rollback, backup, restore, and RLS conventions
   as stable generated contracts.
2. Add readiness/liveness and structured logging conventions for each recipe.
3. Document recovery-time and recovery-point targets as project-owned choices;
   provide verification procedures rather than fixed product assumptions.
4. Provide opt-in infrastructure profiles only where they have a defined
   operational owner and lifecycle; keep the invariant baseline small.
5. Require restore drills and image rollback rehearsal before a generated project
   is declared production-ready.

### Acceptance criteria

- Generated-project operators can identify service health, restore a backup, and
  roll back a migration using documented, tested procedures.

## Delivery order

1. Implement compatibility/manifest foundations.
2. Add governance artifacts and trusted-publisher migration instructions.
3. Strengthen manual verification and recipe tests.
4. Add reproducibility/image inventory documentation and enforcement.
5. Implement read-only doctor and upgrade planning after manifest adoption.
6. Evolve opt-in production profiles only after their operational contracts are
   reviewed.

## Release policy

This roadmap does not authorize automatic pull-request or merge workflows. A
maintainer explicitly runs the release-candidate gate, creates an immutable tag,
and approves publication through the protected release environment.
